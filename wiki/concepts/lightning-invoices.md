# Lightning invoices and the payment lifecycle

The Lightning Network uses a system of invoices instead of addresses. Invoices are generated by the recipient of a payment, and their validity can be limited to a certain amount of time. ([source](../../raw/docs/the-lightning-network/payment-lifecycle.md))

Each invoice is signed by the recipient and contains an amount, expiration time, destination pubkey, supported features and others. Invoices can also be canceled by the recipient. The guide says these mechanisms help eliminate overpayments, underpayments, late payments and duplicate payments, and can be configured to handle tips and partial payments. ([source](../../raw/docs/the-lightning-network/payment-lifecycle.md))

Lightning invoices are defined by the BOLT 11 standard. BOLT stands for "Basis of Lightning Technology" and covers all Lightning Network specifications, which allow separate implementations to function and interact on the same network; a Lightning invoice created by any client or tool will be understood by all other implementations. ([source](../../raw/docs/the-lightning-network/payment-lifecycle/understanding-lightning-invoices.md))

See also: [[multihop-payments]], [[htlc]], [[payment-channels]], [[lightning-network-overview]], [[lnd-receiving-payments]], [[lnd-sending-payments]], [[lnd-invoices]].

## URI scheme

Lightning invoices may be prefixed with `lightning:` to signal in hyperlinks which software can be used to pay the invoice. ([source](../../raw/docs/the-lightning-network/payment-lifecycle/understanding-lightning-invoices.md))

## Structure of an invoice

A Lightning invoice consists of a human readable part and a data part. ([source](../../raw/docs/the-lightning-network/payment-lifecycle/understanding-lightning-invoices.md))

**Case sensitivity.** Lightning Network invoices, like other bech32 encoded strings, are typically entirely lowercase. There are significant space improvements when encoding uppercase characters only in QR codes, which is why uppercase invoices are encountered and why a Lightning invoice QR code might decode as uppercase only. ([source](../../raw/docs/the-lightning-network/payment-lifecycle/understanding-lightning-invoices.md))

**Prefix.** An invoice starts with the letters `ln` for Lightning Network, followed by the same two-letter code as defined by BIP173 for native Segwit addresses, such as `bc` for Bitcoin, `tb` for Testnet Bitcoin, `bs` for Bitcoin signet and `bcrt` for Bitcoin regtest. As the invoice is Bech32 encoded, it also includes the appropriate checksum at the end. ([source](../../raw/docs/the-lightning-network/payment-lifecycle/understanding-lightning-invoices.md))

**Amount.** The prefix is followed by the amount. A typical invoice includes an amount, but it is possible to issue invoices without amounts. Lightning invoices reference bitcoin, not satoshi. To save space, an amount may be followed by a multiplier: a single satoshi invoice would appear as `10n`, a hundred satoshi as `1u`, and a milli-satoshi as `10p`. ([source](../../raw/docs/the-lightning-network/payment-lifecycle/understanding-lightning-invoices.md))

| unit | multiplier | satoshi |
|---|---|---|
| m (milli) | 0.001 | 100,000 |
| u (micro) | 0.000001 | 100 |
| n (nano) | 0.000000001 | 0.1 |
| p (pico) | 0.000000000001 | 0.0001 |

([source](../../raw/docs/the-lightning-network/payment-lifecycle/understanding-lightning-invoices.md))

Prefix and amount together are human-readable. ([source](../../raw/docs/the-lightning-network/payment-lifecycle/understanding-lightning-invoices.md))

**Timestamp.** The first part of the data part is a unix timestamp. ([source](../../raw/docs/the-lightning-network/payment-lifecycle/understanding-lightning-invoices.md))

**Tagged fields.** A number of tags may be used to indicate additional data; some of that data is required, while other fields can be optionally supplied by the payee. The source lists the following as currently defined:

| Tag | Meaning as given by the source |
|---|---|
| `p` (1) | The 256-bit SHA256 payment_hash. The preimage is later revealed as part of the payment process and can act as proof of payment. |
| `s` (16) | A 256-bit secret that prevents forwarding nodes from probing the payment recipient. |
| `d` (13) | A short description of the purpose of payment, encoded with UTF-8. If this field is not set, tag `h` has to be used instead. |
| `n` (19) | The 33-byte public key of the payee node may be included here. |
| `h` (23) | If field `d` does not provide space, a hash of the longer description may be included here. How the full description gets communicated is not defined. |
| `x` (6) | The expiry time in seconds. |
| `c` (24) | The min_final_cltv_expiry for the last HTLC in the route. Typically defaults to 18. |
| `f` (9) | A fallback on-chain address, in case the Lightning payment fails. |
| `r` (3) | One or more entries containing extra routing information for a private route. |
| `9` (5) | One or more 5-bit values containing features supported or required for receiving this payment. |

([source](../../raw/docs/the-lightning-network/payment-lifecycle/understanding-lightning-invoices.md))

The routing hints in the `r` field include a pubkey (264 bits), short_channel_id (64 bits), fee_base_msat (32 bits, big-endian), fee_proportional_millionths (32 bits, big-endian) and cltv_expiry_delta (16 bits, big-endian). ([source](../../raw/docs/the-lightning-network/payment-lifecycle/understanding-lightning-invoices.md))

**Signature.** Finally, the invoice includes a signature, which is verified using the public key provided in the invoice. ([source](../../raw/docs/the-lightning-network/payment-lifecycle/understanding-lightning-invoices.md))

## Decoding an invoice

Any Lightning invoice can be decoded to inspect its contents with the command `lncli decodepayreq`. The source's decoded example shows the fields `destination`, `payment_hash`, `num_satoshis`, `timestamp`, `expiry`, `description`, `description_hash`, `fallback_addr`, `cltv_expiry`, `route_hints` (with `hop_hints` entries holding `node_id`, `chan_id`, `fee_base_msat`, `fee_proportional_millionths` and `cltv_expiry_delta`), `payment_addr`, `num_msat` and `features`. ([source](../../raw/docs/the-lightning-network/payment-lifecycle/understanding-lightning-invoices.md))

The example invoice in the source begins `lnbc20m1` and decodes to `"num_satoshis": "2000000"`, `"num_msat": "2000000000"`, `"expiry": "3600"` and `"cltv_expiry": "9"`. ([source](../../raw/docs/the-lightning-network/payment-lifecycle/understanding-lightning-invoices.md))

## LNURL

A Lightning Network URL, or LNURL, is a proposed standard for interactions between a Lightning payer and payee. A LNURL is a bech32 encoded url prefixed with lnurl. The Lightning wallet is expected to decode the url, contact the url and await a json object with further instructions, most notably a tag defining the behavior of the lnurl. LNURLs are most commonly used to initiate withdrawals or create static payment links. ([source](../../raw/docs/the-lightning-network/payment-lifecycle/understanding-lightning-invoices.md))
