# L402

L402 (Lightning HTTP 402 Protocol) is a standard to facilitate the authentication and trade of services such as API endpoints and computational resources. The guide says it is built with a focus on agentic commerce, with the stack optimized for interaction between AI agents. ([source](../../raw/docs/the-lightning-network/l402.md))

The glossary describes the L402 protocol as combining Macaroons with preimages as proof of payment to create tickets for paid APIs or other services that require authentication and payment, and says it is named after the HTTP 402 error code. ([source](../../raw/docs/community-resources/glossary.md))

## How it works

1. Request: the client, which may be a user's wallet, a program or an agent, sends an HTTP request to an L402-gated endpoint. ([source](../../raw/docs/the-lightning-network/l402.md))
2. Response: the server responds with `HTTP 402 Payment Required` and a `WWW-Authenticate` header containing a token and a Lightning invoice. The token commits to the Lightning invoice by containing the invoice's payment hash. ([source](../../raw/docs/the-lightning-network/l402.md))
3. Payment: the client confirms the conditions laid out in the response and pays the Lightning invoice. There are no restrictions on what wallet or node the payment comes from, as long as the client obtains the preimage as proof the payment was made. ([source](../../raw/docs/the-lightning-network/l402.md))
4. Access: the client presents the token together with the preimage to the API endpoint. The endpoint can verify that the token is valid, and that the payment was made, without access to the payment database (stateless verification). ([source](../../raw/docs/the-lightning-network/l402.md))

As the token is a bearer instrument, the client can pass it on, for example to other agents and wallets, and can further attenuate and restrict it. For instance, a client holding a token for cloud storage may restrict it to read access, or to specific directories, before passing it on to another agent or sub-service. ([source](../../raw/docs/the-lightning-network/l402.md))

## What an L402 is

Lightning API keys (L402) are Macaroons that include a payment hash; to be valid, an L402 must be presented together with the preimage corresponding to the payment hash. The Macaroon is transmitted to the user over HTTP together with a Lightning invoice and contains the payment hash of the invoice as a caveat. See [[macaroons]] and [[lightning-invoices]]. ([source](../../raw/docs/the-lightning-network/l402/l402.md))

A valid L402 therefore consists of two pieces of information: the partial L402, being the Macaroon including the payment hash, and the preimage, which can be obtained by paying the Lightning invoice. ([source](../../raw/docs/the-lightning-network/l402/l402.md))

As the payment hash is a hash of the preimage, and as the preimage can only be obtained by paying the Lightning invoice in full, anyone with the root key can verify that the L402 was issued by the appropriate authority, that it carries the relevant capabilities, and that the Lightning invoice has been paid. This authentication occurs without requiring access to a central database of users or invoices. ([source](../../raw/docs/the-lightning-network/l402/l402.md))

The overview page says the L402 specification is compatible with all bearer tokens that can commit to a payment hash, and that the recommended token format is Macaroons. In practice a service can hand out Macaroons together with Lightning invoices but does not need to validate specifically whether the invoices have been paid: the cryptographic validity of the Macaroon guarantees that the payer obtained the preimage through their payment. ([source](../../raw/docs/the-lightning-network/l402.md))

## Required contents of the Macaroon

To make for a valid L402, a Macaroon must carry the following in its identifier ([source](../../raw/docs/the-lightning-network/l402/l402.md)):

- Version, which allows for an iterative macaroon design: `version = 0`. ([source](../../raw/docs/the-lightning-network/l402/l402.md))
- User identifier, 32 random bytes that allow services to track users across distinct macaroons, useful for service level metering. It is used instead of the macaroon's identifier because the latter can be revoked, e.g. in the case of a service tier upgrade. Example: `user_id = fed74b3ef24820f440601eff5bfb42bef4d615c4948cec8aca3cb15bd23f1013`. ([source](../../raw/docs/the-lightning-network/l402/l402.md))
- Payment hash, which links an invoice's payment request to the macaroon. Example: `payment_hash = 163102a9c88fa4ec9ac9937b6f070bc3e27249a81ad7a05f398ac5d7d16f7bea`. ([source](../../raw/docs/the-lightning-network/l402/l402.md))

### Caveats

There is no limit to what caveats a service may define. Each caveat is a key and value pair separated by an equal (=) sign. For Lightning Labs services, three types of caveats are used. ([source](../../raw/docs/the-lightning-network/l402/l402.md))

- Target services: the caveat `services` lists which services an L402 is authorized to access, as a comma separated list of services and their tier, with the basic tier being 0. Example, Lightning Loop at tier 0: `services = lightning_loop:0`. ([source](../../raw/docs/the-lightning-network/l402/l402.md))
- Service capabilities: these caveats have `_capabilities` appended to the service name, followed by a comma separated list of capabilities the holder may access. If this caveat is not present, the holder has full access to the service. If multiple caveats of this kind exist in the same L402, each must be more restrictive than the previous one. Example: `lightning_loop_capabilities = loop_out,loop_in`. ([source](../../raw/docs/the-lightning-network/l402/l402.md))
- Service constraints: each service capability can be further constrained in a separate caveat beginning with the service capability; again each constraint needs to be more restrictive than the previous. Example allowing the user to Loop out two million satoshis per month only: `loop_out_monthly_volume_sats = 2000000`. ([source](../../raw/docs/the-lightning-network/l402/l402.md))

## Verification

To verify an L402, the server requires the root key with which the original Macaroon was created. This lets the server verify, line by line and caveat by caveat, that the Macaroon was issued by the appropriate authority and that each caveat was properly amended. Finally, the preimage is verified against the payment hash. ([source](../../raw/docs/the-lightning-network/l402/l402.md))

## Wire format

The "L402" authentication scheme transmits credentials as `<macaroon(s)>:<preimage>` pairs, where the preimage is encoded as hex and the Macaroon is encoded as base64. Multiple Macaroons are base64 encoded individually and listed comma separated before the colon. The scheme uses the Authentication Framework specified in RFC 7235; the scheme name is "L402" and is case-insensitive. ([source](../../raw/docs/the-lightning-network/l402/protocol-specification.md))

### HTTP

Upon receipt of a request for a URI of an L402-proxied backend service that lacks credentials, or contains an L402 that is invalid or insufficient in some way, the server should reply with a challenge using the 402 (Payment Required) status code, with a `WWW-Authenticate` header indicating the L402 authentication scheme and the macaroon needed for the client to form a complete L402. The specification's example ([source](../../raw/docs/the-lightning-network/l402/protocol-specification.md)):

```
HTTP/1.1 402 Payment Required

Date: Mon, 04 Feb 2014 16:50:53 GMT

WWW-Authenticate: L402 macaroon="AGIAJEemVQUTEyNCR0exk7ek90Cg==", invoice="lnbc1500n1pw5kjhmpp5fu6xhthlt2vucmzkx6c7wtlh2r625r30cyjsfqhu8rsx4xpz5lwqdpa2fjkzep6yptksct5yp5hxgrrv96hx6twvusycn3qv9jx7ur5d9hkugr5dusx6cqzpgxqr23s79ruapxc4j5uskt4htly2salw4drq979d7rcela9wz02elhypmdzmzlnxuknpgfyfm86pntt8vvkvffma5qc9n50h4mvqhngadqy3ngqjcym5a"
```

Here `"AGIAJEemVQUTEyNCR0exk7ek90Cg=="` is the Macaroon the client must include for each of its authorized requests, and the `lnbc1500n1pw5kjhmpp...` string is the invoice the client must pay to reveal the preimage. ([source](../../raw/docs/the-lightning-network/l402/protocol-specification.md))

To receive authorization, the client pays the invoice from the server, thus revealing the invoice's preimage, and constructs the L402 by concatenating the base64-encoded Macaroon(s), a single colon (":"), and the hex-encoded preimage. The header then looks like this ([source](../../raw/docs/the-lightning-network/l402/protocol-specification.md)):

```
Authorization: L402 AGIAJEemVQUTEyNCR0exk7ek90Cg==:1234abcd1234abcd1234abcd
```

A Macaroon or preimage containing control characters or colons is to be considered an invalid L402 and should result in a 402 and authentication information as above. ([source](../../raw/docs/the-lightning-network/l402/protocol-specification.md))

### gRPC

The gRPC scheme transmits credentials as the same `<macaroon(s)>:<preimage>` pairs. The L402 proxy determines whether an incoming HTTP request is gRPC by checking whether the Content-Type header begins with application/grpc, so gRPC clients must set this header in all requests. The L402 proxy must be HTTP/2 compatible to accommodate requests for gRPC backend services. ([source](../../raw/docs/the-lightning-network/l402/protocol-specification.md))

For a request lacking L402 credentials, the server should reply with a challenge encoded in the grpc-status-details-bin HTTP header as a serialized gRPC Status proto message. Once deserialized it looks roughly like this ([source](../../raw/docs/the-lightning-network/l402/protocol-specification.md)):

```
{
    code: 402,
    message: "missing L402",
    details: {
        type_url: "type.googleapis.com/google.rpc.QuotaFailure",
        value: {
        macaroon: "<macaroon>",
        invoice: "<invoice>"
        }
    }
}
```

Alongside the serialized status details, the server should specify status code `200 OK`, the `Content-Type` header, and the trailers `grpc-message` and `grpc-status`. After extracting the Macaroon and invoice, the client pays the invoice and constructs the L402 identically to the HTTP specification, sending the same `Authorization: L402 <macaroon>:<preimage>` header field. ([source](../../raw/docs/the-lightning-network/l402/protocol-specification.md))

### Reusing credentials

An L402 is intended to be reused until it is revoked and the server issues a new challenge in response to a request containing a newly invalid L402. Possible revocation conditions include expiry date, exceeded N usages, and volume of usages in a certain time period necessitating a tier upgrade. An L402 could be configured for use on a per-backend-service basis or for all Lightning Labs services, because all services are gated by the same L402 proxy, which verifies all Macaroons for all backend services. ([source](../../raw/docs/the-lightning-network/l402/protocol-specification.md))

### Security considerations

The scheme is not considered a secure method of user authentication unless used in conjunction with some external secure system such as TLS, as the Macaroon and preimage are passed over the network as cleartext. If a client's L402 is intercepted, the interceptor can use it and the L402 proxy would not be able to distinguish this usage as illicit. ([source](../../raw/docs/the-lightning-network/l402/protocol-specification.md))

L402 authentication is also vulnerable to spoofing by counterfeit servers: a client that mistypes the URL of a backend service may connect to a server that maliciously stores their L402 and uses it for its own purposes. Requiring the user of the L402 to have a specific IP address could address this, with downsides; for example, the credential becomes unusable if the user switches WiFi networks. ([source](../../raw/docs/the-lightning-network/l402/protocol-specification.md))

## Quickstart

### As a client

Buying L402-gated resources needs no specialized software; at a minimum, Curl and access to a Lightning wallet or API. ([source](../../raw/docs/the-lightning-network/l402/l402-quickstart.md))

1. Request a resource, for example `curl https://lightningfaucet.com/api/l402/headers`. ([source](../../raw/docs/the-lightning-network/l402/l402-quickstart.md))
2. Extract the macaroon and Lightning invoice from the response. Save the macaroon and pass the invoice to your Lightning payment service. ([source](../../raw/docs/the-lightning-network/l402/l402-quickstart.md))
3. Pay the Lightning invoice. It may be paid by your node, a service you run, a wallet API or another service; the only requirement is that the service can provide the preimage once the payment is successful. ([source](../../raw/docs/the-lightning-network/l402/l402-quickstart.md))
4. Assemble the L402 from the macaroon and preimage: `<macaroon>:<preimage>`. ([source](../../raw/docs/the-lightning-network/l402/l402-quickstart.md))
5. Re-request the resource, passing the L402 as part of the header. The quickstart's Python example sets `headers = {"Authorization": f"L402 {macaroon}:{preimage}"}` and calls `requests.get(resource_url, headers=headers)`. ([source](../../raw/docs/the-lightning-network/l402/l402-quickstart.md))

### As a server

A server needs an L402 proxy, such as Aperture. The proxy needs a connection to a Lightning Network node or service to generate invoices. Whether an L402 is valid can be verified using only the root key of the macaroon, without checking with the node whether the payment was received. ([source](../../raw/docs/the-lightning-network/l402/l402-quickstart.md))

## Aperture

Aperture is an implementation of the L402 standard. It functions as a reverse HTTP proxy with support for gRPC and REST requests, forwarding requests with a valid L402 to the relevant API endpoint while issuing Macaroons and Lightning Network invoices to new users. Aperture is used by Lightning Loop. The overview says Aperture allows pricing for API endpoints on the fly, including automatic tier upgrades, per-request pricing or surge pricing. See [[aperture]], [[running-aperture]] and [[aperture-pricing-and-services]]. ([source](../../raw/docs/the-lightning-network/l402.md))

## Implementations and users

Implementations and libraries listed by the guide: Aperture (a gRPC/HTTP authentication reverse proxy using L402), lsat-js (a utility library for working with L402), boltwall (Nodejs middleware-based authentication using L402), now-boltwall (the Boltwall deployment toolkit) and the Aperture Dynamic Pricing Demo. ([source](../../raw/docs/the-lightning-network/l402/implementations-and-links.md))

Projects listed as using L402: Satring (a repository for L402 endpoints), WoT Scoring (an L402-gated way to discover Nostr networks of trust), Lightning Pool, Lightning Loop and the L402 Playground. See [[pool]] and [[loop]]. ([source](../../raw/docs/the-lightning-network/l402/implementations-and-links.md))

## Product ideas from Lightning Bulb

The Lightning Bulb page says implementing L402s is most attractive in services that require metered or paid access together with granular access control, and that a key advantage is that the logic of collecting payments can be separate from verifying access, often without the need to maintain customer records. ([source](../../raw/docs/community-resources/lightning-bulb.md))

Its initial ideas for L402 powered products are a Bitcoin price API (free usage up to a limit, then an L402 with an invoice; or a "delay" caveat so free requests are served after a few seconds), a Virtual Private Network selling bandwidth, a Voice over IP gateway, podcasts and movies (where a subscriber can share an attenuated L402 for a single episode), and cloud storage. It also suggests using L402s for a decentralized metered container execution service. ([source](../../raw/docs/community-resources/lightning-bulb.md))
